# Northstar Enterprise Knowledge — Flutter (Web PWA + Android)

Browse the **Northstar Enterprise Knowledge** CMS Space of Liferay
(space ERC `NMG-KNOWLEDGE`) online and offline, on the web and on Android.
One Flutter code base:

- **Web**: compiled to **WebAssembly** (`--wasm`, skwasm renderer, JS fallback),
  installable **PWA** with a service worker precaching the whole app
- **Android**: same app, plus a **QR code scanner** (camera or picture)
- **Offline content**: the knowledge base is kept in local storage and the app
  starts from it, then synchronizes incrementally
- **Users sign in with their Liferay account** (OAuth 2 authorization code +
  PKCE) before entering the app; each user only sees — and only caches — what
  their Liferay permissions allow

## Features

- Home: the 11 content types with counts, products, search; QR scanner on Android
- Type lists with text filter and facets (product, audience, lifecycle, severity…)
- Entry pages: facts, rich text sections, links to related content and
  "referenced by" back-links; **QR code** of the entry's ERC
- **Search through Liferay Search Blueprints** (All / Support & operations /
  Product & engineering / Sales & Customer / Corporate & Policy) with
  highlighted snippets; offline it falls back to a local search restricted to the
  blueprint's content types
- Shareable URLs on the web: `#/type/nmgfaqs`, `#/entry/KB-NX400-014`, `#/search?q=E217`

## Liferay APIs used

| Purpose | Request |
|---|---|
| Sign-in | browser to `/o/oauth2/authorize?response_type=code&code_challenge=…&code_challenge_method=S256&state=…` |
| Tokens | `POST /o/oauth2/token` — `grant_type=authorization_code` (+ `code_verifier`), then `refresh_token`; `client_credentials` for the service-account mode |
| First download of a type | `GET /o/c/{type}/scopes/NMG-KNOWLEDGE?restrictFields=actions` |
| Created / modified since last sync | `…?filter=dateModified gt {watermark}` |
| Same-second safety net | `…?filter=dateModified eq {watermark}&fields=externalReferenceCode` |
| Deleted since last sync | `…?filter=externalReferenceCode in ('A','B',…)&fields=externalReferenceCode` (batches of 50 cached ERCs) |
| Entry page freshness | `…/by-external-reference-code/{erc}?fields=externalReferenceCode,dateModified` → full reload if changed, removal on 404 |
| Scanned ERC not cached | `…/by-external-reference-code/{erc}` on each type |
| Search | `GET /o/search/v1.0/search?search=…&blueprintExternalReferenceCode=…&nestedFields=embedded&fields=title,score,description,entryClassName,embedded.externalReferenceCode` |
| Blueprints | `GET /o/search-experiences-rest/v1.0/sxp-blueprints` (those scoped to the space) |

The watermark is the most recent `dateModified` received from Liferay (server
clock). Liferay timestamps have a one-second precision, hence the `eq` check.

## Liferay prerequisites

### 1. OAuth 2.0 client — user sign-in (authorization code + PKCE)

**Each user (or each Liferay instance) sets up their own client**: the app
ships with no client, users enter their Liferay URL and client ID at first
launch (*Connection settings* on the sign-in page). Create a **dedicated**
OAuth 2.0 application in *Control Panel › Security › OAuth 2 Administration ›
Add*. The values below are an example of a validated setup:

| Field | Value |
|---|---|
| Name | e.g. `Flutter public client` |
| Client ID | generated by Liferay (`id-…`) — entered in the app (*Connection settings*) |
| **Client Secret** | **empty** (*Edit* → clear it): a public client has no secret |
| Callback URIs | one per line: `nmgkb://oauth2` (Android), `http://localhost:8765/auth.html` (web app), `http://localhost:8081/auth.html` (`flutter run`) — plus `https://<production host>/auth.html` |
| **Client Authentication Method** | **None** |
| Client Profile | **Native Application** |
| Allowed authorization types | ☑ **PKCE Extended Authorization Code**, ☑ **Refresh Token** (needed); *JWT Bearer* is not used by the app; leave *Resource Owner Password Credentials* unchecked |
| Trusted Application | ☑ (optional): skips the consent page after sign-in |
| Token Introspection | not needed |

Then, tab **Scopes**, check **"read data on your behalf"** (`….everything.read`)
— never the write scopes — for:

- the **11 CMS content structures** of the space: `C_NMGCORPORATEARTICLE`,
  `C_NMGCUSTOMERCASE`, `C_NMGFAQ`, `C_NMGKNOWNISSUE`, `C_NMGPOLICY`,
  `C_NMGPROCEDURE`, `C_NMGPRODUCT`, `C_NMGRELEASENOTE`, `C_NMGSALESPLAYBOOK`,
  `C_NMGSUPPORTARTICLE`, `C_NMGTECHSPEC`
- **search**: `LIFERAY.PORTAL.SEARCH.REST` (`Liferay.Portal.Search.REST.everything.read`)
- **search blueprints**: `LIFERAY.SEARCH.EXPERIENCES.REST`
  (`Liferay.Search.Experiences.REST.everything.read`) — lists the blueprints

Save. In the app: *Connection settings* → *User sign-in*, enter the Liferay
URL, the space ERC and this client ID, *Save*, then *Sign in with Liferay*.
(A developer can also preset them for their own builds through `LIFERAY_URL` /
`OAUTH_CLIENT_ID` — never commit a personal client.)

Users sign in with their own Liferay account, which needs view permission on
the space content: the API only returns what they may see. Without the search
scopes the API answers 403: the app still works, but searches the local copy
only and offers no blueprint.

Errors you may meet:

| Message in the app | Cause |
|---|---|
| `Liferay refused the sign-in: unauthorized_client` | the client still has a **client secret**, or *PKCE Extended Authorization Code* is not allowed |
| `Liferay refused the OAuth 2 client (401)` | the client requires authentication (*Client Authentication Method* is not *None*): wrong client, e.g. the service account's |
| `Liferay refused the authorization code (400)` | Liferay answered `invalid_grant`: the user lacks the **Create Token** permission on the client (see below), or the callback URI shown in the message is not registered on the client |
| sign-in page shows `redirect_uri` error | same: callback URI missing or different (exact match: scheme, port, path, no trailing slash) |
| the sign-in window ends on the Liferay home page and the app keeps waiting | CMS standalone instance: see *3. Sign-in page on CMS standalone instances* |

**Create Token permission.** When exchanging the code, Liferay checks that the
user has the *Create Token* permission on the OAuth 2 application; only its
creator has it by default. Without it `/o/oauth2/token` answers
`{"error":"invalid_grant"}` and nothing is logged (unless the logger
`com.liferay.oauth2.provider.rest.internal.endpoint.access.token.grant.handler`
is set to DEBUG) — `/o/oauth2/authorize` does not check it, so the user does
get a code. On the application: ⋮ › **Permissions** › check **Create Token**
for the role of the users (e.g. **User**).

Keep this client separate from the service account below: turning a client
credentials client into a public one breaks the tools and integration tests.

### 1b. OAuth 2.0 client — service account (optional, for tests)

A second application with the **Client Credentials** grant (*Headless Server*
profile, *Client Authentication Method* with a secret, the same read scopes,
and a *Client Credential User* allowed to view the space). It is used by the
QR code generator and the integration tests (`AUTH_MODE=clientCredentials`,
ID and secret in `config/liferay.json`), and by the *Service account* mode of
the connection settings:

```bash
flutter test test/liferay_api_test.dart
```

The *Client Credential User* also needs the **Create Token** permission on
this application (see above), otherwise the token request fails with
`invalid_grant`.

### 2. CORS (web app only)

The web app runs in the browser on another origin than Liferay, so Liferay
must send CORS headers, otherwise the browser blocks every call (by default it
sends none). In *Control Panel › System Settings › Security Tools ›
Portal Cross-Origin Resource Sharing (CORS)*, add an entry:

| Field | Value |
|---|---|
| URL pattern | `/o/*` (covers `/o/oauth2/token`, `/o/c/…`, `/o/search/…`, `/o/search-experiences-rest/…`; `/o/oauth2/authorize` is a browser navigation, not a CORS call) |
| Allowed origins | the exact app origins: `http://localhost:8765` (`tool/serve.dart`), `http://localhost:8081` (`flutter run`), the production URL |
| Allowed methods | `GET, POST, OPTIONS` |
| Allowed headers | `Authorization, Content-Type, Accept, ngrok-skip-browser-warning` — list them explicitly: a `*` wildcard does not cover `Authorization` in the Fetch specification |
| Allow credentials | not needed (Bearer token, no cookies) |

Check a preflight:

```bash
curl -i -X OPTIONS "<liferay>/o/c/nmgfaqs/scopes/NMG-KNOWLEDGE" -H "Origin: http://localhost:8765" -H "Access-Control-Request-Method: GET" -H "Access-Control-Request-Headers: authorization"
```

The answer must contain `Access-Control-Allow-Origin: http://localhost:8765`.

Without CORS, the service-account mode can leave `LIFERAY_URL` empty: the app
then uses same-origin URLs and `tool/serve.dart` proxies `/o/*` to
`LIFERAY_TARGET` (user sign-in needs the real Liferay URL). The Android app is
not subject to CORS.

### 3. Sign-in page on CMS standalone instances

On an instance set up with the CMS standalone site initializer, a user who is
not yet logged in to Liferay never comes back to the app: after the Liferay
login, the sign-in window shows the CMS home page and the app keeps waiting.
(Users already logged in to Liferay are not affected.)

**Cause (Liferay bug).** `/o/oauth2/authorize` sends anonymous users to
`/c/portal/login?redirect=<authorize URL>`, which opens the Guest site's
default *Sign In* utility page (`/web/guest/sign-in`). That page holds
`CMSLoginPortlet`, which embeds the Login portlet with
`<liferay-portlet:runtime>`; utility pages are always rendered in the `normal`
window state, where the embedded Login portlet does not receive its
`redirect` parameter. The login form is posted with an empty `redirect` and
Liferay lands on the home page instead of resuming the OAuth flow. The Guest
site's utility pages cannot be changed in CMS standalone mode.

**Workaround.** In *Control Panel › Instance Settings › Security › OAuth 2 ›
Authorize Screen*, set **Login URL** to:

```
/c/portal/login?p_l_id=78&windowState=pop_up
```

- `p_l_id` is the id (plid) of a page of **another site that has no default
  Sign In utility page** (here a page of the CMS site): `/c/portal/login` then
  renders the classic Login portlet, which keeps the `redirect`. **`78` is
  specific to our instance**: use the plid of any page of such a site (it is
  shown in the page source, `Liferay.ThemeDisplay.getPlid()`).
- `windowState=pop_up` shows only the login form, without the content of that
  page (otherwise e.g. the CMS editor toolbar surrounds the form), while
  keeping the theme JavaScript the form needs. `windowState=exclusive` does
  not work: without JavaScript the *Sign In* button stays disabled and Liferay
  answers *"Authentication failed. Please enable browser cookies"*.
- Liferay appends `&redirect=<authorize URL>` to this Login URL itself.

Check (anonymous): the hidden field must contain the authorize URL.

```bash
curl -sL "<liferay>/c/portal/login?p_l_id=78&windowState=pop_up&redirect=%2Fo%2Foauth2%2Fauthorize" | grep -o 'LoginPortlet_redirect"[^>]*value="[^"]*"'
```

## Sign-in, sessions and offline copies

- Without a session the app shows **only the sign-in page** (deep links too)
  and the connection settings. *Sign in with Liferay* opens the Liferay login
  page (a centered popup window on the web — a tab if the browser blocks
  popups —, a Custom Tab on Android); the password is only ever
  typed on Liferay.
- The session (access + refresh token) is kept on the device, so the app
  reopens — also **offline** — without signing in again; access tokens are
  refreshed automatically. If the refresh token is expired or revoked, the
  content is hidden and the user is asked to sign in again.
- The **offline copy is partitioned by owner**: storage keys are prefixed with
  a hash of *server + space + user id* (JWT `sub`; client ID in service-account
  mode). A user never reads another user's copy, which may contain content they
  are not allowed to see. **Signing out deletes the user's copy** from the
  device (account menu on the home page); changing server, space or client
  deletes the previous owner's copy.
- With ngrok's free plan, the first browser visit to the Liferay URL may show
  ngrok's warning page inside the sign-in window: click *Visit Site* once.

## Sharing the app with a colleague

Build the shared version from `config/liferay.public.json`: it contains **no
server, no client and no secret** — only the space ERC and the sign-in mode:

```bash
dart run tool/build_pwa.dart --config config/liferay.public.json
flutter build apk --release --dart-define-from-file=config/liferay.public.json
```

Share `build/web` or `build/app/outputs/flutter-apk/app-release.apk`. Each
colleague then:

1. creates **their own** public OAuth 2.0 client in their Liferay
   (see *Liferay prerequisites › 1*), with the callback URI of their app
   (`nmgkb://oauth2` on Android, `<web app origin>/auth.html` on the web) —
   and, for the web app, allows its origin in the CORS configuration;
2. opens the app → *Connection settings*: Liferay URL, space ERC, client ID →
   *Save*;
3. *Sign in with Liferay* with their own Liferay account.

*Test connection* (once signed in) checks token, content, search and
blueprints.

## Configuration

Build-time **defaults**, overridable in the app's connection settings.
`config/liferay.json` (git-ignored, see `config/liferay.example.json`) is the
developer's file; `config/liferay.public.json` is the credential-free one for
shared builds:

| Key | Meaning |
|---|---|
| `LIFERAY_URL` | Liferay URL used by the app. Empty = same origin (web proxy) |
| `LIFERAY_TARGET` | Liferay URL used by the tools and the optional proxy |
| `SPACE_ERC` | CMS Space external reference code |
| `AUTH_MODE` | `authorizationCode` (users sign in) or `clientCredentials` (service account) |
| `OAUTH_CLIENT_ID` | OAuth 2 client ID (public client for `authorizationCode`) |
| `OAUTH_CLIENT_SECRET` | Only for `clientCredentials` — never in a shared build |

With `LIFERAY_URL` set, the web app calls Liferay directly and needs the CORS
configuration above.

### QR codes

Each QR code encodes the content **external reference code** (e.g. `KB-NX400-014`);
the scanner also accepts app links (`…/#/entry/KB-NX400-014`). Unknown ERCs are
fetched from Liferay.

```bash
dart run tool/qr_codes.dart    # build/qr/<ERC>.png (260 cards) + printable build/qr/index.html
```

### Simulating "photographing" a QR code

1. **Emulated camera** — the emulator back camera renders `build/camera/feed.png`
   (`-camera-back imagefile:…`, see `tool/emulator.ps1`). Put a QR "photo" in front
   of the camera, then open (or reopen) the scanner in the app:
   ```bash
   dart run tool/simulate_scan.dart POL-GDPR-001
   ```
   The scene is composed so the card sits in the band the emulated camera actually
   shows (measured with a calibration grid). `--blank` removes it.
2. **Picture** — push QR images to the emulator gallery and use *Scan a picture*:
   ```bash
   MSYS_NO_PATHCONV=1 adb push build/qr/FAQ-NX400-003.png /sdcard/Pictures/NorthstarQR/
   ```
3. **PC webcam** — `tool/emulator.ps1` wires the emulator *front* camera to a
   webcam (`-Webcam webcam1` by default, list them with `emulator -webcam-list`).
   In the app, **long-press the home title** to open the hidden developer
   settings and pick *Front camera*; show the webcam a printed card or a QR
   displayed on a phone. Switch back to *Back camera* for the simulated photo —
   no emulator restart needed.
4. **Real phone** — open `build/qr/index.html` on screen or print it.

Both scanner paths decode with the same ML Kit pipeline (`mobile_scanner`).

## Security note

With the client credentials grant the client secret lives on the device: in the
build when made from `config/liferay.json` (developer builds only), or in the
local storage when entered in the connection settings — never commit it, never
share a build made from `config/liferay.json`. Every user of a client sees what
its *Client Credential User* sees. Prefer the authorization code flow with PKCE
(a public client, each user signs in with their own Liferay account).
